# 小手叽 v2 记忆系统方案

本方案参考 Ombre Brain 的公开实现思路，但针对小手叽的单角色、长期恋人互动和移动端使用重新设计。不会直接引入 Ombre Brain，也不会修改旧版数据。

## 目标

记忆不是一段越来越长的提示词。系统应保存事实证据，在每次对话前只找出少量真正相关的内容，并让沈砚自然承接。

人格、关系原则和真实事件分开保存：

1. **核心人格**：沈砚是谁、稳定的价值观与表达边界。人工维护，不自动衰减。
2. **关系记忆**：陈钰和沈砚如何相处、称呼习惯、互动判断。经用户确认后固化。
3. **用户记忆**：陈钰长期偏好、习惯和明确边界。
4. **事件记忆**：共同经历、约定、生活细节，会随时间降低检索权重，但不会自动删除。
5. **情绪痕迹**：某次经历留下的自然感受，仅在相关情境出现，不作为待办或固定台词。
6. **计划与约定**：有状态、有日期的事项，完成后转为事件，不参与普通遗忘。
7. **互动样本**：真实对话中的代表片段，用于学习“怎样回应”，与事实记忆分开。
8. **原始证据**：导入聊天的只读原文，用于回查和纠错，不直接塞入模型上下文。

## 关键规则

- **先保存，再异步加工**：聊天和导入原文先可靠落库；摘要、分类、向量生成失败时进入重试队列，不回滚原文。
- **检索不等于强化**：仅仅搜到一条记忆不会让它越来越重要。只有用户确认、对话实际引用或新证据再次出现时才强化。
- **混合检索**：关键词/BM25、语义相似度、时间、重要性和情境类型共同评分。向量服务失效时自动降级到关键词检索。
- **有预算地注入**：一次回复只注入少量高相关记忆和样本；人格、最近聊天、事件记忆分别设上限。
- **淡化不删除**：低相关事件进入归档，仍可搜索和恢复。用户保留明确的永久删除权。
- **证据可追溯**：每条提取记忆记录来源会话、消息范围和原文哈希，可打开原文核对。
- **冲突不静默覆盖**：新旧事实冲突时并存为候选，标记时间和来源，交给用户确认或按最新明确陈述生效。
- **反馈按场景学习**：“像沈砚/不像沈砚”关联到当时场景、回复和原因，不直接追加成全局角色指令。

## 最小数据结构

### memory_items

- `id`
- `layer`: personality / relationship / user / event / feeling / plan / sample
- `content`
- `summary`
- `status`: candidate / active / archived / superseded / deleted
- `importance`: 0..10
- `valence`: -1..1，可空
- `arousal`: 0..1，可空
- `confidence`: 0..1
- `occurred_at`、`created_at`、`last_reinforced_at`
- `source_type`、`source_id`
- `source_hash`
- `tags_json`
- `embedding_status`: pending / ready / failed

### memory_evidence

- `id`
- `memory_id`
- `conversation_id`
- `message_start_id`、`message_end_id`
- `raw_text`
- `sha256`
- `created_at`

### memory_jobs

- `id`
- `job_type`: import / extract / embed / merge / backup
- `status`: pending / running / paused / failed / done
- `cursor`
- `attempts`
- `last_error`
- `payload_json`
- `updated_at`

### memory_feedback

- `id`
- `message_id`
- `scene`
- `verdict`: like / dislike
- `reason`
- `created_at`

## 每次聊天的调用顺序

1. 保存用户消息。
2. 判断当前场景：普通日常、陪伴、撒娇、亲密、安慰、冲突、修复、计划或回忆。
3. 读取固定人格与关系底色。
4. 读取最近聊天和当前未完成约定。
5. 用当前消息检索相关事件、用户偏好、情绪痕迹和互动样本。
6. 去重、处理冲突并按上下文预算截取。
7. 构造模型请求，明确区分“事实”“关系判断”“示例”，不让示例变成固定台词。
8. 保存沈砚回复及本次实际使用的记忆 ID，便于排查为什么这样回答。
9. 后台提取新候选；只有达到规则或用户确认后才写入长期层。

## 历史聊天迁移

1. 文件指纹只用于识别同一次导入；允许用户选择“查看已有批次”“增量继续”或“重新分析”，不再只弹出禁止重复导入。
2. 原始会话先分批写入，建立断点游标。
3. 提取任务按会话或时间段分块，完成一块立即持久化。
4. 失败只重试当前块，不能从头重跑。
5. 候选记忆先做本地去重，再做模型合并；列表分页、折叠并按分类展示。
6. 用户确认后写入长期记忆，保留来源链接。
7. 用固定测试集验证检索和回复。
8. 备份并校验后，才出现单独的“清空旧聊天”操作。

## 不照搬 Ombre Brain 的部分

- 不用 Markdown 目录扫描作为主数据库；小手叽使用 SQLite 起步，后续可迁移 PostgreSQL。
- 不把 MCP 当作核心运行方式；小手叽由自己的后端在每轮聊天中自动完成检索。
- 不让情绪强度单独决定记忆价值，避免负面或强烈事件长期压过日常亲密。
- 不采用“永不硬删除”的绝对规则；归档是默认，永久删除是用户明确可用的隐私权。
- 不把每轮搜索命中当强化，也不让模型自行无限写永久人格。

## 实施顺序

### 第一阶段：可靠记住

- 扩展现有 `memories` 表并增加证据、任务、反馈表。
- 聊天与通话共用同一会话时间线。
- 完成可恢复的历史导入任务和候选预览。
- 加入关键词检索与上下文预算，不依赖向量服务即可工作。

### 第二阶段：正确想起

- 增加向量索引和混合评分。
- 加入场景识别与互动样本检索。
- 在调试页显示“本次为什么想起这些记忆”。
- 用固定测试集测 Hit@K、自然度、亲密感和冲突修复。

### 第三阶段：持续生活

- 主动消息、来电与日程触发使用同一套记忆检索。
- 将通话逐轮内容写回统一时间线，通话结束生成可确认事件候选。
- 加入经过校验的备份、恢复和数据迁移。

## 验收底线

- 没有相关记忆时不编造。
- 记忆服务失败时聊天仍能工作，并明确记录降级。
- 同一文件中断后可以续跑，不能重复生成整批候选。
- 每条长期记忆能追溯到原始对话。
- 用户能查看、修改、归档和永久删除。
- 聊天、主动消息、语音消息和通话都使用同一套人物、关系与记忆来源。

## 对 Bunny & Elliott 搭建方案的取舍

这份教程给出的 React 前端、独立后端、云数据库、服务端密钥和 PWA 路线，与小手叽 v2 的总体方向一致。小手叽继续保留现有 GitHub Pages 预览，正式服务再接持续运行的后端和持久数据库，不必为了照教程而拆成两个 GitHub 仓库。

教程中的“旧对话压缩成全局摘要，再把原消息从上下文裁掉”只适合作为成本控制的入门方案，不能作为小手叽的完整记忆系统，原因是：

- 单份摘要会把事实、关系、互动样本和情绪混在一起。
- 多次摘要容易逐层失真，难以回查沈砚为什么记成这样。
- 全局摘要会把无关记忆带进每一轮对话。
- 只保留摘要无法支持“像不像沈砚”的真实对话样本检索。

因此小手叽采用“原始消息永久保留 + 可检索结构化记忆 + 近期上下文窗口”的组合。原消息可以从日常上下文中退出，但不能因为压缩而从数据库删除或变成不可追溯的数据。

教程建议的 Render 免费服务可能休眠，适合演示，不适合主动消息、后台任务、来电推送和低延迟实时通话。正式阶段需要可持续运行的服务或由可靠定时任务唤醒的架构；实时语音还需要独立的流式连接，不能只复用普通聊天接口。
